## §2 실제로 나온 것

**지어낸 숫자가 하나도 남지 않았습니다.** 접속자 `1,284`는 실제 WebSocket 연결
수로(연결 전에는 아예 표시 안 함), 좌석 `347/500`은 실제 0으로, 지역 4구분은
정규화된 7권역으로 바뀌었습니다.

**좌석 배정은 UPDATE 한 문장 안에서 끝납니다.** 처음엔 "다음 빈 좌석을 읽고 → 쓴다"로
짰는데 동시 확인 12건에서 재시도가 O(n)으로 터졌습니다. 지금은 SQLite가 문장 내부에서
최소 미사용 번호를 고르고 `RETURNING`으로 돌려주므로 읽기·쓰기 간극 자체가 없습니다.

**`keel` 플러그인을 만들어 이 리포에 처음 적용했습니다.** 로컬 게이트가 푸시를
가로막는 훅이 실제로 두 번 작동했습니다.

## §3 이번 세션이 반증한 것

**세션 시작 시점의 전제 두 개가 틀렸습니다.**

1. **"백서 숫자와 사이트 숫자가 일치하면 정합성 검증 완료"** — 아닙니다. 두 문서가
   서로 같다는 것과 옳다는 것은 다릅니다. 백서의 `signalsPerUsd`는 공개 자료 두
   건으로 교차 확인했지만 1차 출처(Tesla 콘솔)는 여전히 미확인이고, 픽스처
   `_verification` 블록에 그 상태를 그대로 적어뒀습니다. **다음 세션은 이 파일을
   "검증됨"으로 읽으면 안 됩니다.**

2. **"Resend API 키를 받으면 메일 문제가 풀린다"** — 안 풀렸습니다. 요금제가
   도메인 1개 한도이고 그 자리는 kbeauty.market이 쓰고 있어 teslam.io도
   agentba.se도 추가 거부됩니다. 키 자체는 정상이며 실발송으로 확인했습니다
   (`kbeauty.market` → `app.2weeks@gmail.com`, id `8bd951dc…`).

**그리고 제가 만든 결함 두 개를 실증이 잡았습니다.**

- 머신 미러(`llms.txt`)를 고칠 때 6곳 중 2곳만 바꿔, 페이지는 2,108원인데 미러는
  2,107원이었습니다. 각 스위트가 **자기 자신과만** 정합해서 아무도 못 잡았고,
  빌드 산출물 두 개를 직접 비교하고서야 드러났습니다.
- CodeRabbit P1: 워커는 `mailSent: false`를 정직하게 보고하는데 **폼이 그걸
  무시하고 "메일을 확인하세요"라고 말했습니다.** 이 PR이 테스트로 막아온 실패를
  아무도 안 보던 곳에서 저질렀습니다.

공통점은 **테스트가 없던 경로**라는 것입니다. 네 건 모두 회귀 테스트를 붙였습니다.

### 메일을 살리는 3단계

전부 사장님 계정 작업입니다. 코드 변경도 재배포도 필요 없습니다.

1. **Workspace 관리콘솔** — `teslam.io` 보조 도메인 추가, `noreply@teslam.io` 별칭 생성
2. **Google Cloud** — OAuth 클라이언트 소유 프로젝트에서 Gmail API 활성화,
   리다이렉트 URI에 `http://127.0.0.1:8787/callback` 추가
3. **동의 1회** — 발신 계정으로 로그인한 상태에서
   `node scripts/gmail-refresh-token.mjs <client_id> <client_secret>`
   → 리프레시 토큰과 이어서 실행할 `wrangler secret put` 4줄을 출력

그전까지 등록은 저장되고 폼이 *"확인 메일을 보내지 못했습니다"* 라고 표시합니다.
**이 상태는 버그가 아니라 설계된 동작입니다.**
